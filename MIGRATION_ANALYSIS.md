## From Streamlit + Google Sheets → Django + React + Mobile + PostgreSQL

**Analysis Date:** May 12, 2026  
**System:** Fly-Ash Brick Manufacturing ERP  
**Status:** Reference Document for Future Django + React Implementation  
**Target Stack:** Django REST Framework + React + React Native + PostgreSQL

---

## EXECUTIVE SUMMARY

The Flyash system is a comprehensive brick manufacturing management ERP built with:
- **Current Frontend:** Streamlit (Python web framework)
- **Current Backend:** Google Sheets API (gspread) as primary data store
- **Current Infrastructure:** Streamlit Cloud with Google Cloud Platform

**Migration Goal:** Create a scalable, production-ready system with Django REST Framework backend, React web frontend, React Native mobile app, and PostgreSQL database.

**Scale:** ~13 modules, ~40+ database tables, complex business logic for manufacturing, sales, reconciliation, and financial tracking.

## 4. BUSINESS PROCESSES & WORKFLOWS

### 4.1 Raw Material Management
1. **Entry Point:** `views/entry_raw_material.py:render()`
2. **Workflow:**
   - Select Supplier → fetches Material_Type from Suppliers table
   - Input: Material, Qty, Rate, GST, Vehicle_No, Trip_Days, Route_Expenses, Diesel, Driver_Salary, Vehicle_Charge, Freight, Amount_Paid
   - Validation: Qty > 0, Rate > 0, Material required
   - Auto-calculations:
     - Material_Rate = Qty × Rate
     - Total_Cost = Material_Rate + GST + Route_Expenses + Diesel + Driver_Salary + Vehicle_Charge + Freight
   - Generate RM_ID with log ID generator
   - Insert into Raw_Material_Log
   - **Trigger:** Stock_Log recomputed
3. **Validation Rules:**
   - Material_Rate should = Qty × Rate
   - Total_Cost should = Material_Rate + GST
4. **Data Display:** Editable data_editor with deletion support

### 4.2 Production Entry
1. **Entry Point:** `views/entry_production.py:render()`
2. **Workflow:**
   - Input: Date, No_of_Bricks, Cement_Consumption
   - Auto-calculations:
     - FlyAsh_Consumption = No_of_Bricks × flyash_per_brick / 1000
     - StoneDust_Consumption = No_of_Bricks × stone_dust_per_brick / 1000
   - Labour Basis (Day or Contract):
     - If Day: show avg_daily_wage (from Labour table), calculate Labour_Expense
     - If Contract: show contract_rate, calculate Labour_Expense = No_of_Bricks × Contract_Rate
   - Labour_Payment_Date: auto-calculated from payment_week_range
   - Generate Prod_ID with log ID generator
   - Insert into Production_Log
   - **Trigger:** Stock_Log recomputed
3. **Attendance Sync:**
   - If Labour Attendance marked for same date, automatically syncs:
     - Updates No_of_Labour from attendance count
     - Recalculates Labour_Expense if not Contract basis
4. **Validation Rules:**
   - No_of_Bricks > 0
   - Labour validations based on basis

### 4.3 Sales Order Entry
1. **Entry Point:** `views/entry_sales.py:render()` (complex module)
2. **Workflow:**
   - Select Customer → auto-fills GST from Customers
   - Input: Date, Destination, Product, HSN Code, Qty, Sale Rate (or Rate), Freight Rate
   - **Complex Rate Logic:**
     - If Sale Rate provided: decompose into Rate + GST + Freight
       - base_rate = sale_rate / 1.12
       - gst_per_brick = sale_rate - base_rate
       - rate_ex_freight = base_rate - freight_rate
     - If Rate provided: calculate amounts forward
   - Auto-calculations:
     - Amount = Qty × Rate
     - Freight = Qty × Freight_Rate
     - GST = Amount × 12%
     - Total_Amount = Amount + GST + Freight
     - Adjusted_Rate = (Amount + Freight) / Qty (rounded up)
     - Adjusted_Amount = Adjusted_Rate × Qty
     - Adjusted_Total_amount = Adjusted_Amount + GST
   - Invoice_No: auto-generated per financial year (FY##/#### sequence)
   - **Complex Dues Calculation:**
     - Dues = Adjusted_Total_amount - Amount_Received
     - Sign detection: use historical pattern matching to determine positive/negative
   - Generate Sales_ID with log ID generator
   - Insert into Sales_Log
   - **No trigger for Stock_Log** (sales don't affect inventory in this system)
3. **Validation Rules:**
   - Date required
   - Customer required
   - Qty > 0
   - Amount calculations must match expected formulas
4. **Invoice PDF Generation:**
   - Available for each sale
   - Uses reportlab to generate professional invoice
   - Embeds company logo, signature, QR code (from secrets)

### 4.4 Labour Attendance
1. **Entry Point:** `views/labour_attendance.py:render()`
2. **Workflow:**
   - Select Date
   - Display all Active Labour (Active_Status == "Active")
   - Mark Present/Absent (checkbox)
   - On Save:
     - Create/update Labour_Attendance records for date
     - Auto-sync with Production_Log for same date:
       - If no Production_Log entry for date: create with No_of_Labour = present_count
       - If Production_Log entry exists: update No_of_Labour and Labour_Expense
   - **Calculation:** Labour_Expense = present_count × avg_daily_wage (for Day basis only)
3. **Validation:** Active labour exist

### 4.5 Payment Processing
1. **Entry Point:** `views/payments.py:render()`
2. **Workflow:**
   - Input: Date, Customer, Invoice_No (optional), Amount_Paid, Mode
   - On Save: Insert into Payments table
   - **Auto-Reconciliation:**
     - Matches payment against Sales_Log invoices
     - If Invoice_No provided: match that invoice
     - Else: match by Amount + Date (within tolerance window)
     - Allocates payment to outstanding sales (FIFO by date)
     - Updates Sales_Log: Amount_Received, Dues, Payment_ID, Payment_Mode, Payment_Date
     - Updates Payments: Invoice_No (comma-separated if multi-invoice), Payment_Status (Settled/Partially Settled)
3. **Reconciliation Function:** `_reconcile_payments(payments_df, sales_df)`

### 4.6 Stock Management
1. **Computation:**
   - **Stock_Log = Raw_Material_Log + Production_Log**
   - For each material, per date:
     - Opening = previous day's closing
     - Received = sum(Raw_Material_Log entries for material on that date)
     - Used = sum(Production_Log consumption on that date)
     - Closing = Opening + Received - Used
2. **Trigger:** Automatic recomputation when Raw_Material_Log or Production_Log changes
3. **Display:** Stock view shows latest stock per material, historical log
4. **Manual Trigger:** "Recalculate Stock" button

### 4.7 Expense Tracking
1. **Entry Point:** `views/expenses.py:render()`
2. **Workflow:**
   - Input: Date, Category, Subcategory, Amount, Description, etc.
   - Auto-verification: Check if date matches any Sales_Log date (for audit)
   - Generate Expense_ID with log ID generator
   - Insert into Expenses
3. **Verification Status:** Shows "Verified (N sales matches)" or "Not Verified"
4. **Categories:** Office Expense, Operational, Tractor, Diesel, Machine Parts, Other
   - Each category has subcategories (Food, Electricity, Labour, Tractor Diesel, etc.)

### 4.8 Bank Reconciliation (Advanced)
1. **Entry Point:** `views/reconciliation.py:render()`
2. **Data Sources:**
   - Bank_Statement: manual entry of bank transactions
   - Sales_Log: customer receipts
   - Raw_Material_Log: supplier payments (Amount_Paid)
   - Production_Log: labour payments (Actual_Payment_Amount)
3. **Matching Logic:**
   - For Credits (incoming):
     - Match by Invoice_No in narration (if configured)
     - Match by Amount + Date (within tolerance)
   - For Debits (outgoing):
     - Match supplier payments by Amount + Date
     - Match labour payments by keyword + Amount + Date
4. **Reconciliation Output:**
   - Shows matched/unmatched transactions
   - Provides match confidence (Reference, Amount+Date, Keyword)

### 4.9 Master Data Management
1. **Entry Point:** `views/master_data.py:render()`
2. **Workflow:**
   - Edit Suppliers, Customers, Labour in tabs
   - Dynamic row editor (add/delete rows)
   - Auto-generate IDs if missing
3. **ID Maintenance:**
   - "Fill missing IDs": Adds IDs to rows that lack them
   - "Rebuild all IDs": Force-regenerates all IDs, updates all foreign keys across system
4. **Validation:** Required fields per entity type

### 4.10 Dashboards
1. **Dashboard** (`views/dashboard.py`):
   - Complex visualization module
   - Generates charts using Altair
   - Summary metrics: Total sales, production, expenses, dues
   - Period analysis (Monthly, Quarterly, Yearly)
   - Financial year breakdowns
   - Raw material reconciliation table
   - Monthly totals and day counts
2. **Dashboard-1** (`views/dashboard_1.py`):
   - Alternative dashboard view

## 6. DATA VALIDATION & ERROR HANDLING

### 6.1 Validation Rules
**By Column Type:**

| Type | Rules |
|------|-------|
| Required | Must not be empty/whitespace |
| Numeric | Must be convertible to float; if "min" specified, must be >= min |
| Date | Must parse to valid date |
| Email | Not implemented (could be added) |
| FK | Referenced ID must exist in parent table |

**Numeric Columns:** Use `pd.to_numeric(errors="coerce")` → NaN for invalid
**Date Columns:** Use `pd.to_datetime(dayfirst=True, errors="coerce")`
**Lookup:** Check if value exists in parent table

### 6.2 Business Rule Validation
**Formulas:**
- Material_Rate = Qty × Rate (±0.01 tolerance)
- Total_Cost = Material_Rate + GST (for raw materials)
- Total_Amount = Amount + GST + Freight (for sales)
- Dues = Total_Amount - Amount_Received (for sales)

**Constraints:**
- No duplicate Invoice_No per FY
- Labour_ID must exist in Labour table
- Supplier_ID must exist in Suppliers table
- Customer_ID must exist in Customers table
- Date must be valid

### 6.3 Error Handling
**Google Sheets API:**
```python
try:
    get_spreadsheet()
except Exception as exc:
    st.sidebar.error("Google Sheets connection failed")
    st.sidebar.caption(str(exc))
    st.stop()
```

**Cell Not Found:**

try:
    cell = worksheet.find(row_id, in_column=id_col_index)

## 15. ADDITIONAL NOTES

### 15.1 Known Limitations (Current System)
1. **No user authentication:** All users see all data
2. **Single-user concurrency:** Google Sheets API not optimized for simultaneous writes
3. **No audit trail:** Can't see who changed what when
4. **Google Sheets limitations:**
   - 5M cell limit per sheet
   - No ACID transactions
   - Slow for large datasets
   - Limited query capabilities
5. **Frontend coupling:** Business logic scattered in Streamlit views
6. **No API:** Only accessible via Streamlit UI

### 15.2 Improvements in Migration
1. Proper authentication & authorization
2. Audit trail on all changes
3. Proper database with transactions
4. RESTful API for programmatic access
5. Mobile app support
6. Better performance (database queries vs API calls)
7. Scalability (PostgreSQL can handle 100M+ rows)
8. Separation of concerns (Django models, serializers, views)
9. Testing infrastructure (unit, integration, E2E)
10. Background job processing (Celery for PDF generation, reconciliation)

### 15.3 Data Preservation Strategy
```
Phase 1: Export all GSheets data to CSV
Phase 2: Create PostgreSQL schema
Phase 3: Data migration script (validate, transform, load)
Phase 4: Implement Django models with same business logic
Phase 5: Build React UI with API integration
Phase 6: User acceptance testing (UAT)
Phase 7: Parallel run (old system + new system)
Phase 8: Cutover
Phase 9: Decommission old system
```

### 15.4 File References for Migration Team

**Core Logic Files (Must Preserve):**
- `utils.py`: All calculation and validation functions
- `database.py` ID generation and validation logic: models → Django ORM
- `views/`: All business logic → Django viewsets/services
- `fix_dues.py`: Data maintenance scripts → Management commands

**Frontend Files (Can Rewrite):**
- `main.py`: Router logic → React Router
- `pages/`: UI wrappers → React components
- `app.py`: Entry point → React app entry
